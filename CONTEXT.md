Independent Digital SAT / PSAT practice app. React 19 + Vite frontend, static
build deployed to PythonAnywhere (`https://hdsat.pythonanywhere.com`), Supabase
for accounts and cloud sync, question bank generated by Python under
`supabase/import/`.

## Asking Freebuff to triage reports (this works; do it when asked)

The operator console and this chat share one data path. When the owner says
"check the reports" / "what appeals are open", run the local CLI — it needs
`.pa/supabase_url` and `.pa/supabase_service_key` (both gitignored; never print
the key, never paste rows containing email addresses into a public place):

```bash
python tools/admin_triage.py digest                  # markdown brief: SLA, groups, newest
python tools/admin_triage.py open                    # everything still received/in_review
python tools/admin_triage.py reports --status received --json
python tools/admin_triage.py appeals --limit 20
python tools/admin_triage.py resolve <id>
python tools/admin_triage.py reply appeal <id> --template wrong_key --finding "..." --dry-run
python tools/admin_triage.py reply appeal <id> --template wrong_key --finding "..." --yes
```

Replies use a fixed shape (reference → what you sent → what we found → what we
changed → next step). Templates: `wrong_key`, `explanation`, `typo_or_format`,
`mistagged`, `copyright`, `no_fault`, `fixed_thanks`. Every send/close appends a
line to `.pa/triage_log.jsonl`, so "did we already answer this?" is answerable.
Emails are redacted unless `--show-emails` is passed.

Summarise, group by question/reason, and propose fixes; only mutate when the
owner asks. The SQL side is `20261023000100_admin_console.sql` plus
`20261024000100_admin_human_check.sql`, applied to the live project; the console
unlocks with a self-hosted proof-of-work human check plus the operator passcode
(bcrypt hash in `admin_gate`, no privileged account, no `is_admin` flag).

## Definitions worth knowing

- **Mastered** (`QuestionProgress.status`): two *consecutive* correct answers on
  the same item, counted across sessions (`consecutive_correct >= 2`, both in
  `src/lib/storage.ts` and the `submit_question_attempt` RPC). A session never
  repeats an item. Practice draws unseen items first and then only items whose
  **review date** has arrived (`src/lib/review.ts`): a miss is due immediately,
  one correct answer is due after 1 day, and a mastered item returns after
  7/14/30 days depending on how many consecutive correct answers it has. Seen
  items that are not due are never filler; only saved / incorrect-only drills may
  revisit them because the student picked them. A session can therefore be
  shorter than the requested count, which the Practice config states as
  `N ready · M due for review`.
- **SM-2** (`src/lib/sm2.ts`): the flashcard scheduler. Each review's recall
  quality (0–5) nudges an ease factor (floor 1.3); a miss resets the interval to
  1 day, successes step 1 → 3 → 6 → ease×interval, and a 14-day interval marks
  the card `mastered`. The name is intentionally absent from the UI.
- **Storage reality (checked 2026-10-23):** Supabase database is **25 MB of the
  500 MB** free tier — `questions` 9.6 MB (6,193 rows), `question_keys` 2.8 MB,
  `flashcards` 0.5 MB, and **all student data is 0.8 MB across 7 accounts**
  (3 confirmed; 37 tracked attempts, 15 full tests). Roughly 2.1 KB per question
  + key, so the DB alone holds ≈ 300k questions, or the current bank plus about
  285 MB of history. PythonAnywhere holds only the static bundle (bank JSON,
  ≈9.4 MB raw, compressed in transit), which is why it sits at ~38%.
- **Two copies of the bank.** The JSON bundle is the source of truth for guest
  mode (offline, instant filtering); the `questions`/`question_keys` tables are
  the derived copy every cloud RPC writes against. Neither is redundant.
- **Datasets stay separate.** Each source keeps its own row, licence and
  attribution; official College Board items are labelled `Official · …` and are
  never folded into the HDSAT source. `import_questions.py --file` merges them,
  runs the QA gate, writes the bank JSON and the seed SQL (including the new
  source row), and `apply_seed.py` pushes it live.

## Rules of the road

- Guest-first: everything works without an account; local data lives under
  `hdsat.profile.v1`.
- Cloud writes stay behind Supabase RPCs and RLS. Never ship a service-role key.
- New R&W items must be original, single-answer, and pass the importer's
  validation. Prefer genuinely distinct passages over duplicated variants.
- Full tests are strictly fresh-item unless the unseen pool runs out; the
  coverage notice must say so.
- Keep the Bluebook runner visually quiet (grey 1px rules, no rainbow banners).

## 2026-10-25 — Ladders that finish
